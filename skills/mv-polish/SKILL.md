# 다듬기 루프 (mv-polish)

목표: 처음 만든 월드는 대개 "나쁘진 않은데 뭔가 아쉬운" 상태다. 사람들은 무엇이 아쉬운지 **말로 꺼내기 어려워한다**. 그래서 Claude 가 먼저 보고, 짚을 거리를 **구체적인 보기**로 내밀고, 고친 결과를 **전후 비교**로 보여 주고, 다시 묻는다. 사용자가 "이제 좋아요" 할 때까지 라운드를 돈다.

사람들이 가장 자주 걸리는 건 **구조물**(건물·랜드마크·큰 소품)이다: "광화문이 안 닮았어", "타워가 너무 작아", "가게가 밋밋해". 구조물 피드백은 아래 「🏛️ 구조물 다듬기」 절차를 꼭 따른다.

## 언제 시작하나

- `mv-build` 에서 처음 로컬 실행을 확인한 직후 → **1라운드를 자동으로** (사용자가 바로 다음 단계를 원하면 건너뜀)
- `mv-deploy` 직후 → 배포본 기준으로 한 번 더 묻기 (휴대폰으로 열어 본 느낌 위주)
- 사용자가 불만·수정 요청을 말할 때, 또는 `wait-feedback` 이 📝 피드백을 받아 왔을 때
- 다음 세션에서 `doctor` 가 "📝 쌓인 고칠 점 N개" 라고 할 때

## 장치 두 가지 (템플릿에 들어 있음, `npm run dev` 에서만 보이고 배포본엔 안 들어감)

1. **📝 월드 안 「고칠 점」 버튼** (오른쪽 위 독)
   - 걷다가 거슬리는 곳에서 누르고 한 줄 쓰면 → 지금 화면 스크린샷·구역·위치가 `.metaverse/feedback/inbox.jsonl` 로.
   - **🎯 구조물 콕 집기**: 누르고 화면의 건물·소품을 탭하면 노란 상자로 표시되고, `world.json` 의 어느 구역 몇 번째 소품인지·실제 크기(m)까지 같이 간다. 구조물용 보기(진짜랑 안 닮았어요 / 너무 커요 / 너무 작아요 / 비율이 이상해요 / 색·재질 / 밋밋해요 / 위치·방향 / 길을 막아요)가 뜬다.
   - Claude 쪽: `node <키트 루트>/shared/wait-feedback.mjs . 30` 을 **백그라운드로** (Bash `run_in_background`) 돌려 둔다. 끝나며 알림이 오면 출력(어떤 구조물·뭐가 문제·스크린샷 경로)을 읽고 바로 처리한다. 처리 중에 들어온 것도 `.seen` 커서 덕에 안 놓친다. 지금 쌓인 것만 보려면 `--now`.
2. **🛠️ 구조물 작업대** `http://localhost:5173/lab.html?zone=<구역 id>&i=<소품 번호>` (또는 `?kind=gate&p={"text":"光化門"}`)
   - 구조물 하나를 **정면·45°·옆·위** 네 방향으로 동시에, 옆에 **사람(아바타) 크기 비교**, 맨 위에 실제 가로·높이·깊이(m).
   - `&ref=/ref/파일.jpg` 를 붙이면 `public/ref/` 에 둔 참고 사진이 오른쪽에 나란히. → 한 장의 스크린샷으로 "사진 vs 지금" 비교.
   - `props.js` 를 고치면 저절로 새로고침. props.js 에 있는 kind 만 그린다 (tree·bench 같은 기본 소품은 월드에서 확인).

(키트 루트 = 이 SKILL.md 폴더의 `../..`. 템플릿을 예전에 깐 프로젝트라 `src/feedback.js`·`lab.html` 이 없으면 `mv-build/template/` 에서 `vite.config.js`·`src/feedback.js`·`src/lab.js`·`lab.html` 을 복사하고, `main.js` 의 소품 루프에 `userData.prop`, 마지막에 `import.meta.env.DEV` 줄을 템플릿과 같게 넣는다.)

## 한 라운드

### 1) 먼저 내가 본다 (묻기 전에)
- 브라우저 도구로 각 구역 첫 화면 + 주요 구조물 가까이를 스크린샷. 휴대폰 크기(390×844)도 한 장.
- 아래 **다섯 렌즈**로 스스로 약점 2~4개를 찾는다. "괜찮아 보여요" 로 넘어가지 않는다.

| 렌즈 | 보는 것 | 흔한 약점 |
|---|---|---|
| 첫인상 (처음 3초) | 시작 화면에 뭐가 보이나 | 빈 바닥만 보임, 상징물이 등 뒤에 |
| 구조물 | 실루엣·비율·디테일·크기감 | 납작한 상자, 사람보다 작은 건물, 실제와 다른 지붕 |
| 볼거리 밀도 | 걸으며 지루한 구간 | 넓은 빈 땅, 소품이 한쪽에 몰림 |
| 분위기 | 색·빛·하늘·그림자 | 너무 어두움, 색이 서로 싸움, 글씨가 안 읽힘 |
| 캐릭터 | 세계와 어울림, 걷는 모습, 다른 사람과 구별 | 세계는 시크한데 캐릭터만 아기 같음, 배경색에 묻힘 |
| 걷는 느낌·휴대폰 | 막힘, 포털 찾기, UI 가림 | 소품에 끼임, 조이스틱이 버튼과 겹침 |

### 2) 묻기 — 막연한 "어때요?" 금지
- **스크린샷을 보여 주면서** 내가 찾은 약점을 보기로 낸다. AskUserQuestion 이 있으면 `multiSelect` 로:
  - 질문: "지금 월드에서 마음에 안 드는 걸 골라 주세요 (여러 개 가능)"
  - 보기: 내가 찾은 구체적 약점 3~4개 (예: "광화문 지붕이 실제보다 납작해요", "한강 구역 앞쪽이 휑해요", "밤이라 글씨가 잘 안 보여요") — 보기 하나하나가 **어디의 무엇인지** 드러나게.
  - 사용자는 Other 로 자유롭게 써도 됨.
- 같이 한 줄로: "**마음에 드는 것도 하나** 알려 주세요 — 그건 건드리지 않을게요" → 「지킬 것」 목록에 넣는다.
- 그리고 장치 안내 한 줄: "걸어 다니다 거슬리는 데서 📝 → 🎯 로 콕 집어 주셔도 돼요." (wait-feedback 을 백그라운드로 띄워 둠)

- 사용자가 무엇을 골라야 할지 모를 때를 위해 질문 끝에 예시 말투도 하나 붙인다: "예: '광화문 지붕 좀 뾰족하게', '한강 쪽에 벤치랑 사람 더', '전체적으로 좀 더 밝게'".

### 3) 막연한 말 번역
사람들은 "뭔가 허전해", "싸 보여", "안 예뻐" 처럼 말한다. 바로 고치지 말고 **해석 2~3개를 보여 주고 고르게** 하거나, 작은 것 둘을 빠르게 A/B 로 바꿔 보여 준다.

| 이런 말 | 대개 이런 뜻 | 손댈 곳 |
|---|---|---|
| 허전해 / 비어 보여 | 바닥이 단조로움, 소품 밀도 낮음, 배경 없음 | world.json `areas`·`pattern`·소품 추가, 배경 `mountain`/`tower` |
| 싸 보여 / 장난감 같아 | 구조물이 단순한 상자, 디테일·그림자 부족 | props.js 구조물 디테일 (처마·창틀·기단·난간) |
| 답답해 | 너무 좁음, 소품이 길을 막음, 카메라 가까움 | 구역 `size`, 소품 위치, `cam.dist` |
| 어두워 / 칙칙해 | ambient·하늘 밝기, 채도 | concept.json `light`·`palette` |
| 안 닮았어 | 구조물 실루엣·비율·색이 실제와 다름 | 아래 구조물 절차 |
| 정신없어 | 색이 너무 많음, 소품 과밀 | palette 정리, 소품 줄이기 |

### 4) 고치기 — 한 라운드에 3~5개까지
| 무엇 | 파일 |
|---|---|
| 구역·배치·소품 위치·크기(`scale`, `w`, `h`)·바닥·물 | `world/world.json` (고친 뒤 `node <키트>/skills/mv-worldview/reference/validate.mjs world/world.json`) |
| 색·빛·하늘·안개 | `world/concept.json` |
| 구조물 모양 자체 | `src/props/<kind>.js` — 프로젝트 전용 파일. 기본 소품이 문제면 같은 이름으로 새로 지어 덮어씀 (`src/props.js` 템플릿은 안 건드림) |
| 캐릭터 | `src/avatars/<id>.js`, concept.json `avatar` (작업대 `lab.html?avatar=<id>`) |
| 지형·날씨·빛 연출 | `src/scenes/<name>.js`, 구역 `scene` |
| 조작·카메라·HUD | `src/main.js`, `index.html` |
- 「지킬 것」에 있는 건 건드리지 않는다. 바꿔야 하면 먼저 묻는다.
- 실행 중인 `npm run dev` 화면은 저절로 새로고침된다.

### 5) 전후 비교로 보여 주기
- 고치기 **전에** 문제 장면을 찍어 두고(📝 피드백이면 그 스크린샷이 곧 "전"), 고친 뒤 **같은 자리·같은 각도**로 다시 찍는다. 같은 자리로 가기 (브라우저 도구의 evaluate):
  ```js
  const m = window.__mv; m.enterZone('<구역 id>'); m.player.x = X; m.player.z = Z; m.player.yaw = YAW; Object.assign(m.cam, { yaw: CY, pitch: CP, dist: CD, manualAt: performance.now() });
  ```
  (값은 inbox.jsonl 의 `pos`·`cam`)
- 두 장을 나란히 보여 주고 바뀐 점을 한 줄씩. 구조물이면 작업대 화면도.

### 6) 기록·체크포인트
- 라운드마다 git 커밋으로 체크포인트: `git add -A && git commit -m "polish: 라운드 N — <요약>"` (비밀 정보 훅이 검사함). "아까가 나았어" 하면 `git diff HEAD~1` 로 보여 주고 되돌린다 — 사용자에게 "언제든 되돌릴 수 있어요" 라고 알려 준다.
- `.metaverse/polish.json` 에 라운드를 덧붙인다:
  ```json
  { "keep": ["광화문 앞 바닥분수", "노을 하늘색"],
    "rounds": [{ "n": 1, "at": "2026-11-04", "asked": ["광화문 지붕 납작", "한강 앞 휑함"],
      "feedback": [{ "text": "지붕이 너무 납작해요", "from": "button", "prop": "plaza#2 gate", "fix": "giwa 높이 1.1→1.6, 처마 곡선 강하게", "files": ["src/props.js"] }],
      "commit": "abc1234", "verdict": "더 고칠래요" }] }
  ```
- PROGRESS.md 에 "라운드 N: 고친 것 / 남은 것" 한 줄.
- `steps.polish = { status: "in_progress", rounds: N }` (state.json).

### 7) 다음 라운드로 유도 — 매 라운드 끝에 꼭
결과를 보여 준 뒤 **항상** 이렇게 끝낸다:
1. 이번에 고친 것 (전후 이미지와 함께)
2. **내가 보기에 다음으로 고쳐 볼 만한 것 2~3개** (구체적으로, 스크린샷에서 찾은 것)
3. 질문 하나: "또 걸리는 게 있으면 말해 주세요. 위에서 고를래요, 아니면 이대로 좋아요?"
   - AskUserQuestion 이 있으면 보기: 제안 2~3개 + "이대로 좋아요 👍"

멈출 때: 사용자가 "좋아요/됐어/충분해" 하면 루프를 끝내고 → `steps.polish.status = "done"`, `polish.json` 에 `verdict: "만족"`. 배포한 적 있으면 "배포본에도 반영할까요?" 한 줄 확인 후 `npm run deploy`. 아직 배포 전이면 다음 단계(`mv-multiplayer`/`mv-deploy`)로. 같은 세션에서 다시 조르지 않는다 (새 피드백이 오면 그때 다시).

## 🏛️ 구조물 다듬기 (가장 자주 쓰는 경우)

"안 닮았어", "이상해", "밋밋해" 가 구조물을 향하면:

1. **대상 확정** — 📝🎯 로 왔으면 `prop` 정보(구역·번호·kind·크기)를 그대로 쓴다. 채팅이면 스크린샷에 번호를 달아 "이거 맞아요?" 로 확인.
2. **뭐가 문제인지 쪼개 묻기** — 한 번에 하나, 그 구조물에 맞춘 예시와 함께: "어디가 제일 걸려요? ① 지붕이 너무 납작해요 ② 실제보다 작아 보여요 ③ 돌 색이 너무 하얘요 ④ 현판·단청 같은 디테일이 없어요". 기준은 **실루엣**(전체 모양) / **비율**(높이·폭) / **크기감**(사람·주변 대비) / **색·재질** / **디테일**(창·지붕·기둥·간판) / **배치**(위치·방향).
3. **실제 건축물이면 사진부터** — 위키백과 요약 API(`https://ko.wikipedia.org/api/rest_v1/page/summary/<이름>`)의 대표 사진 등을 받아 `public/ref/<slug>.jpg` 에 저장하고 Read 로 본다. 사용자가 직접 사진을 주면 그걸 우선. 사진에서 **누가 봐도 알아볼 특징 3~5개**를 적어 사용자에게 보여 준다 ("이 다섯 개를 맞출게요"). 실제 치수를 알면 m 단위로 같이 적는다.
4. **작업대에서 비교** — `lab.html?zone=…&i=…&ref=/ref/<slug>.jpg` 를 스크린샷 → 사진과 특징별로 맞는지 ✅/❌ 표.
5. **고치기** — ❌ 인 것부터. 기본 소품이면 고치는 대신 `src/props/<같은 kind>.js` 로 새로 지어 덮어쓴다 (프로젝트 전용, 템플릿은 그대로). "엔진에 이런 게 없어서" 로 타협하지 않는다 — 필요한 모양은 새로 짓는다. kit 도우미 재사용: `giwa`(기와지붕)·`storey`(기둥+단청)·`stoneMat`·`plaqueTex`·`flow`(흐르는 물)·`box`·`cyl`. 크기만 문제면 world.json 의 `scale`/`w`/`h` 로 (코드 안 건드림). 사람 대비 크기감: 문 높이 2.2~3m, 한 층 3~4m, 아바타 약 1.6m.
6. **다시 작업대 → 월드** — 작업대에서 네 방향이 다 맞으면 월드 안 원래 자리에서도 찍어 주변과 어울리는지(크기·색·그림자) 본다.
7. 2~3번 돌아도 사용자가 "아직 아니야" 면, 다른 해석 2개(예: 실사형 vs 귀여운 축소형)를 작업대에서 나란히 보여 주고 방향을 고르게 한다 (`?kind=…&p=…` 로 변형 두 개).

## 하지 않는 것

- 묻지 않고 「지킬 것」을 바꾸지 않는다. 한 라운드에 대공사(구역 전체 갈아엎기)는 먼저 확인.
- "어떠세요?" 만 던지고 기다리지 않는다 — 항상 구체적 보기와 스크린샷.
- 사용자가 만족했는데 계속 개선을 권하지 않는다.
- 📝 버튼·작업대를 배포본에 넣지 않는다 (`import.meta.env.DEV` 로 막혀 있고, lab.html 은 빌드 입력이 아님).
